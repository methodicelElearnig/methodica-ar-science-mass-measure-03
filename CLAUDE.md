# Instructions for Claude Code — Methodica mass-measure (720 lomda family)

This file applies to all sub-projects in this directory (`Methodica-science-mass-measure-02-01` through `-06`, and any new Sain added later). Each is an independent HTML/CSS/JS lomda ("Sain") sharing the same template conventions. These bugs happened in this project and must not happen again in future lomdas.

## 1. Companion-character avatar images must never change by themselves a few seconds after the screen appears

Any screen showing the learner's chosen companion character (green/orange) must satisfy ALL of these:

- **No hardcoded default `src`** on the `<img>` tag in HTML (e.g. `src="assets/images/avatar-orange-X.png"`). Leave `src` off entirely — only JS should ever set it.
- **Resolve the avatar image *before* the screen becomes visible.** In `goTo(n)`, `resetScreenState(n)` (which sets `img.src` based on `window.lomdaState.selectedCharacter`) must run **before** `target.classList.add('active')`. If any code path shows a popup/screen via a different route (not through `goTo`, e.g. a "check answer" feedback function), the same rule applies there too — resolve the avatar src before the containing element becomes visible.
- **Preload** both color variants (or at least the resolved one) at script init via `new Image()`, so the very first time a color is needed there's no network/decode delay.

Why this matters: if the screen becomes visible while the `<img>` still shows the old hardcoded/default src, the browser paints the wrong color for one or more frames before the JS-corrected src loads — a visible "wrong character, then it swaps a few seconds later" flash.

**Quick self-check for a new screen:** grep the project for `selectedCharacter ===` to find every avatar read site, then confirm each one's `<img>` has no hardcoded src and runs before its container's visibility is toggled.

## 2. Feedback popup must be draggable from anywhere on it, and it has **no close button at all**

⚠️ **Updated 2026-08-02** — this rule used to say "the X must fully close it." That is now obsolete: per an approved product decision (2026-07-26) recorded in the `720-templates` skill (`_global-components.md` → "Feedback popup system" → "No manual close"), **every feedback popup — correct, incorrect, and message, in every question template — has no close/X button whatsoever.** Not hidden, not disabled: the element must not exist in the DOM, CSS, or JS at all. If you see a `.scq-fb-toggle`/`.scq-fb-close` button, its CSS rule, a `scqFbClose()` function, or an `onclick="scqFbClose(...)"` anywhere, that's leftover pre-2026-07-26 code — remove it, don't "fix" its close behavior.

- **Dragging:** the popup must be draggable from **anywhere on the popup**, not just the title bar. When implementing `scqFbMakeDraggable`-style drag logic, bind `mousedown` to the whole `.scq-fb-box`/popup element. The only elements excluded from starting a drag are legitimate in-popup controls that must remain clickable — e.g. `.scq-fb-reveal-btn` (see rule #4) — via `e.target.closest(...)`. There is no close/toggle button to exclude anymore.
- **The only three approved ways a popup may disappear:** (1) navigating to another screen (`goTo()` closes all popups as part of screen cleanup), (2) starting a new attempt on a question that explicitly supports retry-dismissal (only for non-final incorrect feedback), or (3) an explicit one-way in-question state transition (e.g. the rule-#4 reveal button that toggles between showing the correct answer and the learner's own answer — see rule #4; the popup itself never closes during that toggle, it only swaps displayed text in place, so this stays compliant). Nothing else — no X, no `Escape`, no outside-click, no backdrop-click — may remove a feedback popup.
- There is no "collapsed" state in the spec; if you see a `.collapsed` class being toggled instead of `visible` being removed, that's a bug, not a variant.

## 3. In drag&drop questions, a placed/dropped item's label must never drift toward the wrong side of its slot

When a dragged item (a distractor/word chip) is dropped into a target slot and rendered there — typically a `.dq-placed-card`-style element inside a drop zone (`direction: rtl`, `display: inline-flex`) — the item's internal alignment must use `justify-content: flex-start`, **never** `flex-end`.

- In an RTL flex row, `flex-start` anchors content to the **right** (where it visually belongs, adjacent to the preceding text/slot edge). `flex-end` anchors it to the **left** — the opposite of what it looks like in an LTR mental model.
- This only becomes visible when the slot can be wider than the placed content (e.g. a `min-width` on the drop zone that isn't collapsed to the content size when occupied) — a short label like "טון" or "מסה" gets shoved to the far side of the slot, reading as "the word jumped left after I dropped it."
- The correct reference implementation is `.dq-placed-card` in `Methodica-science-mass-measure-02-05/styles.css` (`justify-content: flex-start`). This bug was introduced in `-02-06` by copying that block but transcribing `flex-end` instead — always copy this rule verbatim, never "fix" it based on LTR intuition.

**Quick self-check for a new drag&drop screen:** grep the project's CSS for `justify-content: flex-end` anywhere inside a `direction: rtl` block that positions a placed/dropped label, and confirm it's `flex-start` (or `center`, if the slot is always sized to fit its content exactly).

## 4. Drag&drop questions capped at 2 attempts must not auto-reveal the correct answer — they need a "התשובה הנכונה" / "התשובה שלי" toggle button

By default, a drag&drop question that locks after a 2nd wrong attempt (`attempts >= 2`) tends to call its `revealCorrect()`-style function immediately and show the final "here's the correct answer" feedback. Per explicit client request, this must instead be **learner-initiated**, with the ability to switch back and forth between the correct solution and the learner's own last answer:

- **Don't auto-reveal.** On the 2nd wrong attempt: mark the zones wrong (as already happened), show a short "pending" feedback text (e.g. `רוצים לראות את הפתרון הנכון?`), and reveal a button inside the feedback popup instead of calling the reveal function.
- **The button** (`class="scq-fb-reveal-btn"`, hidden by default) lives inside the `.scq-fb-box`, after `.scq-fb-body`. Style it like `.btn-hint`: white background, `#019de5` border/text, `border-radius: 1000px`, `font-family: 'Assistant'`, `font-size: 18px`, `padding: 10px 24px` — a secondary pill, not the solid `.btn-continue` gradient.
- **It's a toggle, not a one-shot reveal:**
  - First click ("התשובה הנכונה") → reveal the correct placement (existing `revealCorrect()` logic, unchanged) + show the existing final feedback text (e.g. `wrongFinal`) → relabel the button to **"התשובה שלי"**.
  - Second click ("התשובה שלי") → restore the learner's own last-submitted placement, re-mark each zone correct/wrong against it, and show the "pending" text again → relabel the button back to **"התשובה הנכונה"**.
  - Keeps toggling indefinitely; nothing else about the check flow changes.
- **Snapshot the real answer, don't guess it.** At the exact moment the 2nd wrong attempt is detected (before any reveal), copy the current placement state (which drag item is in which zone, or `'source'`/unplaced for anything never dropped) into a separate variable. `revealCorrect()` overwrites the live placement object, so without this snapshot the learner's original answer is unrecoverable once "התשובה הנכונה" is clicked.
- **Do not reword any existing feedback text** (`correct`, `wrong1`, `wrongFinal`/`wrong2`, etc.) to build this — the only new copy needed is the one "pending" message, reused for both the initial post-2nd-wrong state and every time the learner toggles back to "my answer."
- **Fix the drag-popup exclusion.** Every project has its own copy of `scqFbMakeDraggable(boxId)`, which binds `mousedown` on the whole feedback box to make it draggable (see rule #2). Its exclusion check must exclude `.scq-fb-reveal-btn` (`e.target.closest('.scq-fb-reveal-btn')`), or clicking the new button gets hijacked as a drag-start and does nothing. (Older code additionally excluded `.scq-fb-close`/`.scq-fb-toggle` for the popup's close button — that button no longer exists per rule #2, so don't reintroduce it in that check.)
- **Reset properly.** On a fresh screen load/reset, hide the button, reset its label back to "התשובה הנכונה", and clear the snapshot variable — otherwise a learner who reset the question can inherit stale state from a previous attempt.
- Two implementation shapes exist in this family: the shared `makeDragQuestion(cfg)` factory (used by e.g. Sain 5/6's sentence-fill questions — add a `revealBtnId` key to `cfg` and the toggle lives in the factory itself) and hand-written per-screen code (the `s9`/`s20`/`drag9`-style questions — wire the same toggle logic directly into that screen's own `Check()`/`RevealCorrect()`/`resetScreenState*()` functions). Match whichever pattern the target screen already uses.

**Quick self-check for a new capped-attempt drag&drop screen:** confirm the reveal function is never called automatically inside the wrong-attempt branch of `Check()`; confirm a placement snapshot is taken *before* any reveal happens; and confirm `scqFbMakeDraggable`'s exclusion list includes the new button's class.

## 5. Transition screens (`.transition-content`) must always have one bold sentence (`h2.transition-title`), never an all-`.transition-sub` wall of text

Every `.transition-title-block` (the text stack next to the companion character on a "מסך מעבר" screen) follows the same typographic hierarchy: **one bold headline sentence** — `<h2 class="transition-title">` (Assistant, 40px, weight 700) — plus one or more regular, smaller supporting sentences — `<p class="transition-sub">` (Assistant, ~26–28px, weight 400). This happened repeatedly in `-03-03`, `-03-04`, `-03-05`, and `-03-06`: the whole text block was built as a stack of `.transition-sub` paragraphs with **no `h2.transition-title` at all**, on the reasoning "there's no big number/emphasized word here, so no title was invented."

- **That reasoning is wrong.** The bold sentence doesn't have to be a number (`"5 שאלות"`) — it can be any short phrase (`"זמן טוב ללמוד גם בצורה אחרת,"`, `"משימת שיא 2"`, `"עכשיו מגיעה שאלת השיא"`). Before concluding a transition screen has no title candidate, check the corresponding screen in the reference project (`Methodica-science-mass-measure-02-01` through `-06`, i.e. `02-linked`) — the same or near-identical sentence is almost always already split there into `h2.transition-title` + `p.transition-sub`. Copy that split, don't invent a "no title" exception.
- **The CSS is usually already correct** (`.transition-title`/`.transition-sub` rules exist and are styled correctly) even when the bug is present — this is a **markup-only** bug: the wrong element (`<p class="transition-sub">`) was used instead of `<h2 class="transition-title">` for the headline sentence, so nothing renders bold/larger even though the styling exists and works.
- This is exactly the same "guessed instead of checking the reference" root cause as other bugs in this family — see `search_source_before_inventing` note in `-03-01/styles.css`.

**Quick self-check for a new transition screen:** open `.transition-title-block` in the HTML and confirm it contains at least one `<h2 class="transition-title">` — if every child is a `<p class="transition-sub">`, compare against the equivalent screen in `02-linked` before assuming the design has no bold sentence.

## 6. Every scrollable container (`overflow-y: auto/scroll`) must force its native scrollbar to the physical right — it does NOT get that for free just because the page is RTL

Found (2026-09-08) in **all six** `-03-01` through `-03-06` sub-projects simultaneously, in every scrollable container that existed at the time (`.tbl-content`, `.dq-question-panel`, `.s2-content`, `.s7-content`, `.s13-content`, `.s15-content`, `.s17-content`, and the `#s1-scroll-area`/`#s4-scroll-area` id-scoped variants) — a family-wide bug, not a one-off.

- **Root cause:** every page has `<html dir="rtl">` and `html, body { direction: rtl; }`. `direction` is inherited, so any scrollable element that doesn't explicitly override it stays `rtl` too. Per standard browser behavior (Chrome/Firefox/Edge alike), an element with effective `direction: rtl` and `overflow-y: auto|scroll` renders its **native vertical scrollbar on the LEFT**, not the right — this is true even if the scrollbar is skinned via `::-webkit-scrollbar*` (that only changes its appearance, never which physical side it's on). One project's CSS even had a comment asserting the opposite ("direction:rtl ensures the scrollbar sits on the right") — that comment was wrong; it was actively causing the bug it claimed to prevent.
- **The fix — wrap the children, don't touch them:** the scrollable element itself keeps its class/id and every existing positioning/overflow/padding/scroll-snap declaration, and gains one new line: `direction: ltr;` (this is what pushes the native scrollbar to the physical right edge). Wrap ALL of that element's existing children — unmodified — in one new inner `<div class="<name>-inner">`, and give that new class `direction: rtl;` (restoring true RTL layout for every descendant, since without it they'd inherit the outer `ltr` and silently flip physical sides wherever they rely on inherited direction — e.g. `align-items: flex-start` meaning "physical right"). If the outer element itself declared `display:flex; flex-direction:...; align-items:...; gap:...` to lay out its own children (several of these did), move that whole block onto the new `-inner` class too — it means the same thing again once it's wrapped in `direction:rtl`. If any child relies on percentage height/min-height against the scroll container's own box (e.g. a `min-height:100%` scroll-snap page), give the new `-inner` class `height: 100%;` too, so that percentage basis doesn't silently disappear.
- **Do NOT** try to fix this by touching nested rules (flipping individual `align-items`/`align-self`/`justify-content` values deeper in the tree) — descendants that already declare their own explicit `direction: rtl` (very common in this codebase) are self-contained and must be left alone; the wrapper technique above is what makes that safe.
- **Before shipping the wrapper:** grep the project's CSS for `<outer-selector> >` (child-combinator) or `:first-child`/`:last-child`/`:nth-child` scoped to the outer element, and grep script.js for `.children[`, `.firstElementChild`, `.lastElementChild`, or `:scope >` against it — any of these need to be retargeted through the new `-inner` wrapper (or changed to a class/id-based lookup), since they used to assume the scrollable element's real content sat one level shallower than it now does. `scrollTop`/`scrollTo(`/`scrollHeight`/`clientHeight`/wheel/keydown listeners bound to the outer element's existing id are unaffected — it's still the same element, still the real scrolling one.

**Quick self-check for a new scrollable screen:** grep the project's CSS for `overflow-y: auto` / `overflow-y: scroll` / `overflow: auto` / `overflow: scroll`; for each hit, confirm the element (or a same-box ancestor) has `direction: ltr` and that its actual content sits inside a `direction: rtl` inner wrapper — not directly inside the scrolling element itself.

**The scrollbar's own visual spec (width/colors/border) is a real Figma component — do not eyeball it.** Every `::-webkit-scrollbar*` rule in this family had been copied forward from one project to the next without ever being checked against Figma (an assumption traced back through "SELF-QA.md §7", never verified at the source). Confirmed 2026-09-08 against the actual Figma node (720 - UI Templates, `eSbp4bKHgBky0rakDb8l9N`, node `1723:43076`, named "scrolling"): width **12px** (every project had 8px — wrong), track `background: rgba(201,206,216,0.4)` + `border-radius: 16px` (already correct everywhere) **+ `border: 0.5px solid #f3f4f5`** (missing everywhere), thumb `background: rgba(0,0,0,0.56)` + `border-radius: 24px` (already correct everywhere). Pair the `::-webkit-scrollbar*` rules with a Firefox fallback on the scroll container itself: `scrollbar-width: auto; scrollbar-color: rgba(0,0,0,0.56) rgba(201,206,216,0.4);` (Firefox ignores `::-webkit-scrollbar*` entirely and falls back to the plain OS scrollbar without this). If a future Figma update changes this component, re-fetch node `1723:43076` rather than trusting these numbers indefinitely.

## 7. The scroll gesture-hint hand must sit ON the scrollbar strip, and the hand-shaped hover cursor must be scoped to that same strip — not centered/spread across the whole content box

Two related follow-up bugs found (2026-09-08) after rule #6's scrollbar-side fix, both stemming from treating "the scroll container" and "the scrollbar" as the same region when they're not — the scrollbar is an ~8px strip at the container's physical right edge (per rule #6, these containers force `direction: ltr` on themselves), while the container spans the *entire* content width.

- **Gesture-hint hand position:** `.gesture-hint-scroll-wrap .gesture-hint` must anchor near the container's right edge (`left: auto; right: 10px;`), not `left: 50%` (horizontal center of the whole content box). Centering it in the content looked "aligned" in a static code read (it sits inside the same box coordinates as the scroll container), but the actual product requirement is that the hand sits **on the scrollbar itself**, not floating in the middle of unrelated content. `top: 62%` (vertical position) is unaffected — only the horizontal anchor moves.
- **Hand-shaped hover cursor:** any `.tbl-content`-style scroll container that sets `cursor: grab` directly on itself (documented in SELF-QA.md §7, "the mouse should be in the shape of a hand") is wrong if the container's own box spans most of the screen (it usually does — `top:139px`-ish to `bottom:74px`-ish, full width) — hovering *anywhere* in that huge box shows the grab cursor, which reads as "the whole screen is a hand" rather than "the scrollbar is a hand." Fix: remove `cursor: grab` from the base rule, add `.tbl-content.near-scrollbar { cursor: grab; }` instead, and toggle that class via a shared `initScrollbarHoverCursor(el, thresholdPx)` helper in script.js — a `mousemove` listener that toggles `.near-scrollbar` based on `rect.right - e.clientX <= threshold` (threshold ~20px, generous on purpose so it's easy to hit without pixel-perfect aim). Call it once per scroll container, from the same place `dataset.jumpInit` guards against double-init (e.g. `s16InitScrollJump()`/`s2InitScrollJump()`-style functions).
- Both fixes are pure CSS/JS additions scoped to the existing shared classes (`.gesture-hint-scroll-wrap .gesture-hint`, `.tbl-content`) — they apply to every screen using that class at once, no per-screen markup changes needed.

**Quick self-check for a new scroll screen:** confirm `.gesture-hint-scroll-wrap .gesture-hint` has `right` (not `left: 50%`) for its horizontal anchor; confirm the scroll container's `cursor: grab` (if any) lives on a `.near-scrollbar`-gated rule, not the bare container selector, and that `initScrollbarHoverCursor()` is actually called for that container.

## 8. The drag gesture-hint hand+rings must sit past the target chip's edge, measured from its actual width — never dead-center on it, never a hardcoded pixel guess

`showDragGestureHint(slotEl)` (present with an identical body in every project that has a drag question — s5/s6/s11/s16/s17 in `-03-01`, and the equivalents in `-03-03`/`-03-05`/`-03-06`) appends the hint as a child of the target slot and, by default, centers it dead-center via `.gesture-hint { left: 50%; top: 50%; }` — which sits the hand and rings directly on top of the chip's own label text, hiding it. Found and fixed 2026-09-08, client-reported with a marked-up screenshot.

- **Move the hint's own anchor point, not just the hand.** `.gesture-hint-hand` and `.gesture-hint-ring` both center themselves via their own `translate(-50%,-50%)` around `.gesture-hint`'s position — they are two independent elements sharing one anchor, not one unit. A first attempt at this fix only offset `.gesture-hint-hand`'s own `translate`, leaving the ring animating alone back at the chip's center while the hand floated away disconnected from it — an obviously broken result once actually looked at (the two visually belong together; a hand pointing at nothing while a ring pulses somewhere else makes no sense). The correct fix moves `.gesture-hint`'s own anchor point (or, better, sets it dynamically — see below) so hand and rings move together as the single visual unit they're meant to be.
- **Measure the actual target width in JS — don't hardcode a pixel offset in CSS.** Chip/slot width is not constant: some projects use a fixed `.dq-drag-card { width: 180px }`, `-03-01` screen 17/18's hand-written `.s17-drag-item` is 260px, and some projects (`-03-05`, `-03-06`) use `min-width: 90px` chips that grow to fit their own label text. A single hardcoded `calc(50% + 85px)` calibrated for one project's 180px chip silently under-clears a wider chip elsewhere (still overlapping its text) — this happened on the first pass. The robust fix lives in `showDragGestureHint()` itself, computed per call from the real element: `hint.style.left = 'calc(50% + ' + (slotEl.offsetWidth / 2 + 25) + 'px)';` (`+25` clears both the 28px hand and the wider 42px `.gesture-hint-ring--drag-big`; an even earlier pass used `+10`, enough only for the hand) — `.gesture-hint`'s CSS `left: 50%` stays as the harmless fallback/default, since the inline style always overrides it regardless of the target's actual size.
- Vertical position (`top: 50%`) is correct as-is and untouched — the hint should stay vertically centered on the chip, only the horizontal anchor needed to move past its text.
- **Defer the width read to the next animation frame — don't measure it synchronously inside `showDragGestureHint()`.** Found 2026-09-08: the offset formula above is correct, yet the hand kept covering text on `-03-01` screens 11/16/17 even after applying it. Root cause: `showDragGestureHint()` is always called from inside a screen's `resetScreenState*()`, and `goTo(n)` calls `resetScreenState(n)` **before** `target.classList.add('active')` (this ordering is required by rule #1, for an unrelated reason — avatar `src` resolution). At the moment `showDragGestureHint()` runs, the screen is therefore still `display:none`, so `slotEl.offsetWidth` reads `0` — the formula collapses to `calc(50% + 25px)`, i.e. only 25px past the chip's *center*, not past its *edge*, landing the hand right on the text. Fix: wrap the width read + `hint.style.left` assignment in `requestAnimationFrame(function () { ... })` — by the next frame, `goTo()` has already run `classList.add('active')` synchronously, so the screen is visible and `offsetWidth` is accurate. (Everything else — `hint.className`, the inner HTML, `slotEl.appendChild(hint)`, the dismiss listeners — stays synchronous; only the width-dependent positioning is deferred.)

**Quick self-check for a new drag question using `showDragGestureHint`:** confirm the offset is computed from `slotEl.offsetWidth` inside the function (not a fixed number in CSS); confirm that read is deferred via `requestAnimationFrame` rather than done synchronously in the same tick as `slotEl.appendChild(hint)`; and confirm `.gesture-hint-hand`/`.gesture-hint-ring` have no per-class `translate` override of their own — both must still share the exact same anchor point so they move together.

## 9. Multi-section scroll screens (`.tbl-content`/`.tbl-page`) must be normal continuous flow, not `scroll-snap` "sections" — and a shared action bar across multiple gated questions needs scroll-position tracking, not a discrete page index

The client's standing preference (reconfirmed 2026-09-08 on Sain 5 screen 5, after already saying so earlier in the project) is that any screen built from multiple `.tbl-page` sections inside one `.tbl-content` scroll container must let the learner scroll through them continuously, with each section sized to its own actual content — **not** `scroll-snap-type: y mandatory` + `.tbl-page { min-height: 100%; scroll-snap-align: start; scroll-snap-stop: always; }` forcing every section to be at least one full viewport tall and "jump" between them. The symptom that keeps getting reported is "the scrollbar is abnormally long" — that's the forced `min-height:100%` inflating `scrollHeight` far past the real (usually much shorter) content of each section, so the thumb looks tiny on an oversized track.

- **The conversion itself** (done for `-03-04` screen 3, `-03-05` screen 5, `-03-06` screen 2): remove `scroll-snap-type` from `.tbl-content` (or the ID-scoped variant, if `.tbl-page` is shared with another still-paged screen in the same project — scope the removal to that screen only, e.g. `#s4-scroll-area .tbl-page { min-height: auto; scroll-snap-align: none; scroll-snap-stop: normal; }`, leaving the base rule untouched for screens still using it); remove any `sNGoToPage`/`sNCurrentPage`/`sNJumping`/`sNInitScrollJump`-style wheel/keydown page-jump JS (it exists specifically to fight free scrolling into a discrete "page" model — once sections aren't full-viewport pages anymore, hijacking `wheel`/`keydown` to force a jump feels broken, not smooth).
- **Watch for a shared action bar spanning multiple independently-gated questions.** Some multi-section screens (e.g. `-03-06` screen 2: text → table → 3 separate single-choice/drag questions) don't give each question its own inline check/hint buttons the way `-03-04`/`-03-05` do — they share ONE fixed `#sN-check`/`#sN-hint` bottom bar across all of them, re-bound per "current page" via a `sNSyncBar(index)` dispatcher. Removing the discrete page-index model (previous bullet) leaves nothing driving `index` for that dispatcher. Fix: replace the wheel/keydown-driven index with scroll-position tracking — a `scroll` listener on the container that, on every event, finds whichever `.tbl-page` has its vertical midpoint closest to the container's own visible midpoint, and calls `sNSyncBar(thatIndex)` only when the index actually changed. This is safe to call repeatedly/redundantly as long as each individual sync function (and any `reset()` it triggers, e.g. a `makeDragQuestion` instance) reads its own already-answered/in-progress state rather than unconditionally re-initializing — check that before relying on this pattern for a new screen. Keep the screen's own `sNGoToPage(index)` function alive (just simplified, drop the old `sNJumping` mutual-exclusion guard) for the "המשך" buttons that programmatically advance to the next section on completion — smooth-scrolling there is still wanted, just not for ordinary user-driven scroll input.
- **Do not silently guess which of the two shapes above a given screen needs.** If a screen's `.tbl-page` sections each own their own inline check/hint controls (like `-03-04` screen 3), the plain CSS-only conversion is enough. If they share one external action bar keyed by page index (like `-03-06` screen 2), converting the CSS alone without adding scroll tracking leaves the shared button permanently stuck on whichever section happened to be current when the page loaded. When in doubt, ask before converting — this is a functional/UX fork, not just a visual one.

**Quick self-check across the family:** grep each project's `styles.css` for `scroll-snap-type` / `scroll-snap-align` — any hit still marks an unconverted "sections" screen (as of 2026-09-08, the only one left in the whole active family is `-03-05`'s `#s1-scroll-area`, screen 2 — intentionally not yet touched). For each `.tbl-content` screen found, grep its `index.html` for how many `id="sN-check"`/`onclick="sNCheck"`-style controls exist inside vs. outside the `.tbl-page` sections to tell which of the two conversion shapes above it needs.
